# دستیار و تأیید — فاز ۵

## جریان قابل اجرا

ورود ← فضای حساب شخصی LOCAL/LIVE ← دستیار ← انتخاب سرویس یا درخواست فهرست سرویس‌ها ← ارسال پیام ← ذخیره پیام پاکسازی‌شده ← پیشنهاد ابزار معتبر مدل ← طرح بررسی ← مرور سرویس، بازه، مقصد مدل و داده‌ها ← تأیید صریح ← خواندن اطلاعات سرویس/۵ انتشار آخر/در صورت درخواست ۳۰ خط لاگ ← ذخیره شواهد با شناسه و زمان ← گزارش ساختاریافته فارسی ← بازگشت یا تازه‌سازی همان گفتگو.

مسیر `/workspace/assistant` خصوصی است؛ شناسه گفتگو در query `conversation` قابل بازگشت است. `/demo/assistant` و حالت DEMO همچنان سناریویی، مستقل و بدون تماس با مدل هستند. تاریخچه خصوصی حداکثر ۱۰۰ گفتگو و ۱۰۰ پیام اخیر هر گفتگو را نمایش می‌دهد؛ داده‌های قدیمی حذف نمی‌شوند. زمینه مدل ۱۲ پیام اخیر است و خلاصه ساختاریافته تحلیل قبلی را در حد سقف متن دریافت می‌کند.

## پیکربندی مدل

فقط در محیط سرور تنظیم کنید؛ فایل `.env` موجود را جایگزین نکنید:

```dotenv
AI_BASE_URL=https://api.openai.com/v1
AI_API_KEY=<کلید ارائه‌دهنده>
AI_MODEL=<شناسه مدل مجاز حساب شما>
AI_API_STYLE=responses
AI_TIMEOUT_MS=20000
```

پس از تغییر، API را راه‌اندازی مجدد کنید. کلید یا نام مدل تنظیم‌نشده، فرم را با توضیح روشن غیرفعال می‌کند؛ پاسخ مصنوعی جای مدل واقعی قرار نمی‌گیرد. صفحه تنظیمات API کلید یا URL دارای راز را برنمی‌گرداند. ورودی base URL صرفاً تنظیم مدیر سرور است و از کاربر/مدل دریافت نمی‌شود؛ HTTPS بدون credential/query/fragment لازم است. این تنظیم به معنی پیاده‌سازی SSRF برای URL دلخواه کاربران نیست.

`responses` از `/responses` و `chat` از `/chat/completions` استفاده می‌کند. مدل باید با سبک API و function calling ارائه‌دهنده سازگار باشد؛ نام مدل پیش‌فرض انتخاب نشده است. همه ارائه‌دهندگان سازگار الزاماً تمام فیلدهای این قرارداد را پشتیبانی نمی‌کنند؛ سازگاری باید با همان ارائه‌دهنده بررسی شود. قرارداد از [مستند رسمی function calling](https://developers.openai.com/api/docs/guides/function-calling) بررسی شده است (۲۳ اکتبر ۲۰۲۶). ابزارها JSON Schema strict و `additionalProperties:false` دارند. Responses و Chat شکل متفاوت ابزار و tool_choice دارند؛ adapter هر دو را جداگانه می‌سازد. `store:false` درخواست می‌شود، اما سیاست نگهداری/حساب ارائه‌دهنده مستقل است.

## رجیستری و سقف اجرا

| ابزار | رفتار واقعی | سیاست |
|---|---|---|
| list_applications | حداکثر ۵۰ سرویس از snapshot حساب جاری | فقط خواندن؛ وضعیت cache معیار سلامت نیست |
| inspect_application | ایجاد طرح با applicationId، includeLogs و windowMinutes=15/60/1440 | خود فراخوانی مدل هیچ اطلاعات تازه یا لاگی نمی‌خواند؛ منتظر تأیید |
| report_diagnosis | گزارش summary، facts، hypotheses، missingEvidence و recommendations | فقط پس از شواهد؛ شناسه شاهد ناشناخته رد می‌شود |

هر پیام حداکثر دو فراخوانی مدل دارد (پاسخ/پیشنهاد و در صورت نیاز یک خواندن فهرست). تحلیل پس از تأیید یک فراخوانی دیگر دارد. ابزارها ترتیبی‌اند؛ حلقه آزاد، shell، deploy، restart و mutation ابری وجود ندارد. انتقال نتیجه فهرست، درخواست تازه با داده برچسب‌خورده غیرقابل‌اعتماد است؛ transcript ابزار یا state سمت ارائه‌دهنده نگهداری نمی‌شود. خروجی متنی مدل به صورت متن React نمایش داده می‌شود، نه HTML قابل اجرا.

هر درخواست مدل timeout پیش‌فرض ۲۰ ثانیه، سقف خروجی ۲۵۰۰ توکن و سقف بدنه ۲۵۶ KiB دارد؛ redirect و retry خودکار ممنوع‌اند. API پیام/تصمیم محدودیت ۱۰ درخواست در دقیقه به ازای IP و سقف سراسری موجود دارد. خطای خام ارائه‌دهنده و Authorization به کاربر/لاگ ارسال نمی‌شود. لاگ ارسالی حداکثر ۳۰ خط و هر خط ۱۰۰۰ نویسه است؛ snapshot حجیم با علامت truncated محدود می‌شود. stream توکن و SSE در این فاز وجود ندارد؛ پس از refresh، وضعیت درخواست فعال با polling بازیابی می‌شود.

## تأیید و دوام

طرح شامل نسخه سیاست، LIVE، سرویس/نام/اتصال، credentialVersion، includeLogs، since ثابت، expiresAt، اشتراک با مدل، نام/میزبان مدل و hash تنظیمات مدل است. SHA-256 روی ساختار canonical با ترتیب schema گرفته می‌شود. نام کاربر از نشست و رابطه گفتگو می‌آید؛ body تصمیم فقط hash و approve/cancel می‌پذیرد. تأیید ۱۰ دقیقه اعتبار دارد، با compare-and-swap اتمیک مصرف و audit می‌شود. تغییر پارامتر، snapshot، نسخه اتصال، نام سرویس، مدل یا مقصد ارائه‌دهنده طرح تازه می‌خواهد. پیشنهاد تازه، طرح pending قبلی همان گفتگو را لغو می‌کند.

stateها: PENDING → RUNNING → SUCCEEDED / NEEDS_ATTENTION و PENDING → CANCELLED / EXPIRED. SUCCEEDED یعنی گردآوری شواهد و ثبت تحلیل تمام شده است؛ به معنی سلامت سرویس، اثبات علت یا اعمال اصلاح نیست. طرح مصرف‌شده هرگز خودکار تکرار نمی‌شود. قطع اجرا پس از ۱۸۰ ثانیه در بازخوانی به NEEDS_ATTENTION می‌رود؛ retry فقط با طرح تازه است. lease در PostgreSQL هر گفتگو را بین پردازش‌های API سری می‌کند. پیام‌ها idempotency-key و requestHash دارند؛ replay موفق بدون مدل تازه برمی‌گردد و کلید تغییرکرده/ناموفق/درحال‌اجرا رد می‌شود.

شواهد هر ابزار پیش از درخواست تحلیل ذخیره می‌شوند؛ خطای بعدی آن‌ها را از بین نمی‌برد. مدل فقط با شناسه‌های موجود گزارش می‌دهد. این کنترل صحت معنایی هر جمله را اثبات نمی‌کند؛ UI تحلیل مدل، فرضیه‌ها و کمبود شواهد را جدا می‌کند. پالایش الگوهای رایج و credentialهای شناخته‌شده best effort است؛ همه رازهای احتمالی قابل تشخیص نیستند. کاربر پیش از ارسال شواهد به مدل رضایت می‌دهد. پیام معمولی هم به ارائه‌دهنده تنظیم‌شده ارسال می‌شود و این موضوع کنار composer بیان شده است.

## API

| روش و مسیر `/api/v1` | کاربرد |
|---|---|
| GET /assistant/config | آمادگی، مدل، میزبان و ابزارها، بدون کلید |
| GET/POST /conversations | فهرست/ساخت گفتگو |
| GET /conversations/:id | پیام‌ها، طرح‌ها، شواهد و busy |
| POST /conversations/:id/messages | پیام با UUID idempotency-key |
| POST /conversations/:id/plans/:planId/decision | hash طرح و approve/cancel |

تمام مسیرها نشست/مالکیت دارند و POSTها Origin/CSRF را کنترل می‌کنند. رابط token مدل دریافت نمی‌کند. جزئیات schema در OpenAPI خصوصی موجود است.

## وضعیت تأیید زنده

هیچ کلید مدل واقعی یا credential حساب واقعی لیارا برای این مرحله ارائه نشده است. تست‌های transport هر دو سبک API با fetch fixture، تست API با PostgreSQL واقعی و provider fixture و تست رابط با jsdom انجام می‌شوند. ادعای پاسخ واقعی LLM یا تشخیص سرویس واقعی نمی‌شود. پس از پیکربندی سرور، توکن لیارا فقط در فرم خصوصی اتصال وارد می‌شود و مسیر بالا قابل بررسی است. استقرار، health probe، detector قطعی، incident و اصلاح سرویس متعلق به فازهای ۶ و ۷ هستند.

## اتصال تنظیم‌شده و مدل‌های انتخابی — ادامه فاز ۵ / فاز ۶

درگاه Liara AI از AI_BASE_URL سرور و AI_API_STYLE=chat استفاده می‌کند؛ Responses همان درگاه در آزمون 404 داد. AI_MODEL پیش‌فرض openai/gpt-6.1-sol و AI_MODELS فهرست comma-separated مدل‌های مجاز است: openai/gpt-6.1-sol، openai/gpt-6-luna، openai/gpt-6-astra. مدل از انتخابگر کنار composer برای پیام بعدی تعیین و در Conversation.model ذخیره می‌شود. browser فقط شناسه مجاز را می‌فرستد؛ کلید سرور را دریافت نمی‌کند. API مستقیم OpenAI ممکن است برای همان مدل قرارداد دیگری بخواهد؛ انتخاب سبک درگاه بر اساس آزمون واقعی است.

Sol/Luna در آزمون واقعی chat و tool call پاسخ معتبر دادند؛ Astra در فهرست models بود ولی درخواست آن 402 داشت. MODEL_PAYMENT_REQUIRED با توضیح اعتبار حساب نمایش داده می‌شود؛ این وضعیت به معنی وجود نقص در کلید همه مدل‌ها نیست. تست‌های خودکار همیشه AI_API_KEY واقعی را کنار می‌گذارند؛ تست زنده helper جداگانه scripts/smoke-ai.ts است که حساب موقت را پاک می‌کند و کلید/کوکی را چاپ نمی‌کند.

ابزار plan_deployment فقط طرح انتشار می‌سازد و actionPath داخلیِ ساخته‌شده در سرور را به پیام می‌افزاید. مالکیت، manifest و طرح توسط DeploymentService تعیین می‌شوند؛ tool call هرگز approval یا cloud POST ایجاد نمی‌کند. جزئیات و سقف‌های این ابزار در DEPLOYMENT_WORKFLOW.md است. رجیستری strict در wire schema از format=uri استفاده نمی‌کند چون درگاه آن را رد کرد؛ regex ورودی و بررسی hostname مستقل سمت سرور برقرارند.

مطالب «بدون کلید» و «ابزار انتشار هنوز نیست» در بخش‌های بالاتر، وضعیت تاریخی تحویل اولیه فاز ۵ بودند؛ این بخش وضعیت جاری است. SSE فعلی مربوط به رویدادهای انتشار است، نه استریم توکن مدل. مدل هرگز وضعیت انتشار را از متن خودش موفق اعلام نمی‌کند؛ نتیجه واقعی در صفحه طرح ثبت می‌شود.
