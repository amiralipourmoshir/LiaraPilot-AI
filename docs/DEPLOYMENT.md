# اجرای محلی تا فاز ۶

نیازمندی‌ها: Node 24 LTS، pnpm 11.25.0، Docker با daemon فعال. فایل‌های فونت همراه برنامه‌اند و هیچ درخواست خارجی برای فونت ارسال نمی‌شود.

```sh
cp .env.example .env
pnpm install --frozen-lockfile
pnpm secrets:init
pnpm infra:up
pnpm db:generate
pnpm db:migrate
pnpm dev
```

در نصب مجدد، فایل `.env` موجود خود را جایگزین نکنید. مقادیر نمونه فقط برای محیط توسعه محلی‌اند.

رابط: http://127.0.0.1:5173 — API: http://127.0.0.1:3001. از همین hostname استفاده کنید؛ localhost مبدأ متفاوتی است. Vite درخواست‌های `/api` را به API هدایت می‌کند. پورت‌ها فقط روی loopback بازند. با Ctrl+C سه پردازش برنامه متوقف می‌شوند؛ سرویس‌های دیتابیس و Redis تا `pnpm infra:down` فعال می‌مانند. بدون گزینه حذف volume، داده Docker باقی می‌ماند.

## محیط فعلی بدون Docker daemon

در این محیط PostgreSQL 16 از باینری نصب‌شده و Redis 7 از بسته رسمی Ubuntu، داخل `.local` و روی پورت‌های 55432 و 56379 اجرا شده‌اند. هیچ سرویس موجود سیستم تغییر نکرده است. برای شروع مجدد در همین محیط:

```sh
pnpm infra:local
pnpm db:migrate
pnpm dev
```

helper محلی به PostgreSQL در `/usr/lib/postgresql/16/bin` (یا متغیر `PG_BIN_DIR`) و Redis در `/usr/bin` یا `.local/redis-bin/usr/bin` نیاز دارد. این helper دانلود یا نصب سیستمی انجام نمی‌دهد. فایل‌های `.local` قابل انتقال یا مناسب production نیستند؛ مسیر پیشنهادی نصب تازه Docker Compose است. هم‌زمان از Docker و helper محلی روی پورت‌های یکسان استفاده نکنید.

## مسیر بررسی دستی

۱. صفحه ثبت‌نام را باز کنید، نام، ایمیل و رمز حداقل ۱۲ نویسه بدهید.
۲. تم روشن، تاریک یا سیستم را از بالای صفحه انتخاب کنید. انتخاب در مرورگر ذخیره می‌شود.
۳. پس از ورود، یک پروژه بسازید. صفحه را تازه کنید؛ پروژه باید باقی بماند.
۴. «شروع بررسی زیرساخت» را بزنید؛ درخواست ابتدا در PostgreSQL ثبت و سپس از Redis توسط worker دریافت می‌شود.
۵. نتیجه و رویدادهای ذخیره‌شده را ببینید؛ لینک دارای operation را تازه کنید و همان نتیجه را ببینید.
۶. خارج شوید و با همان ایمیل وارد شوید. پروژه باید در دسترس باشد. حساب دیگر نباید آن را ببیند.

این بررسی محلی است و هیچ انتشار، تحلیل هوش مصنوعی یا اتصال لیارا انجام نمی‌دهد. دریافت نتیجه به اجرای worker نیاز دارد. اگر worker متوقف باشد، درخواست در دیتابیس/صف منتظر می‌ماند و با راه‌اندازی worker ادامه پیدا می‌کند.

## متغیرهای محیطی

| نام | کاربرد |
|---|---|
| NODE_ENV | development/test/production؛ production فقط با APP_ORIGIN از نوع HTTPS |
| HOST / PORT | آدرس و پورت API؛ پیش‌فرض 127.0.0.1:3001 |
| APP_ORIGIN | مبدأ دقیق رابط برای کنترل Origin؛ بدون اسلش پایانی |
| DATABASE_URL | PostgreSQL برنامه؛ credential فقط سمت سرور |
| REDIS_URL | اتصال صف Redis |
| SESSION_TTL_HOURS | عمر نشست؛ پیش‌فرض ۱۶۸ ساعت، بدون تمدید خودکار |
| LOG_LEVEL | سطح Pino؛ داده حساس در خروجی API/لاگ قرار نمی‌گیرد |

## build و اجرا

```sh
pnpm build
pnpm start:api
# در ترمینال مستقل:
pnpm start:worker
```

خروجی رابط در `apps/web/dist` و API/worker در `dist` است. استقرار production به static hosting/reverse proxy برای `/api`، HTTPS، رازهای مستقل و سرویس‌های PostgreSQL/Redis مدیریت‌شده نیاز دارد؛ بسته استقرار نهایی در فازهای بعد تکمیل می‌شود. Vite dev server برای production نیست.

`GET /api/v1/health/live` حیات API و `GET /api/v1/health/ready` دسترسی PostgreSQL/Redis را گزارش می‌کند. آماده بودن این دو، سلامت worker را تضمین نمی‌کند؛ job بررسی محلی مسیر worker را هم بررسی می‌کند. OpenAPI پس از ورود در `/api/v1/openapi.json` قابل دریافت است.

## مشاهده رابط فاز ۳ بدون حساب و سرویس‌های داده

```sh
pnpm install --frozen-lockfile
pnpm dev:web
```

دموی عمومی: http://127.0.0.1:5173/demo

این مسیر برای نمایش UI به PostgreSQL، Redis یا API نیاز ندارد. داده‌ها ثابت‌اند و پاسخ دستیار از سناریوی محلی می‌آید. برای مسیرهای واقعی حساب شخصی از دستور کامل `pnpm dev` و سرویس‌های داده استفاده کنید.

مسیر واقعی بررسی زیرساخت به `/workspace/foundation` منتقل شده است. لینک قدیمی `/workspace?operation=...` به مسیر جدید همان عملیات هدایت می‌شود. در میزبانی static نسخه build، برای مسیرهای `/demo/*` و `/workspace/*` باید fallback به `index.html` تنظیم شود؛ API همچنان باید مستقل و با مسیر `/api` سرو شود.

## اتصال لیارا

پس از ورود، `/workspace/connections` فرم خصوصی توکن دارد؛ نتیجه در `/workspace/applications` دیده می‌شود. توکن را در گفتگو یا فایل عمومی قرار ندهید. `pnpm secrets:init` کلید تصادفی ۳۲ بایتی را فقط در `.env` ایجاد می‌کند و کلید موجود را تغییر نمی‌دهد. نبود کلید باعث رد اتصال جدید می‌شود.

`CREDENTIAL_KEY` باید base64 استاندارد کلید ۳۲ بایتی باشد؛ `CREDENTIAL_KEY_VERSION` پیش‌فرض `v1` است. `LIARA_TIMEOUT_MS` پیش‌فرض ۱۰۰۰۰ و بازه مجاز ۱۰۰ تا ۳۰۰۰۰ میلی‌ثانیه دارد. در production کلید را از secret manager تزریق و مستقل از دیتابیس پشتیبان‌گیری کنید. تغییر یا حذف کلید بدون مهاجرت credentialها دسترسی به توکن‌های قبلی را از بین می‌برد؛ چرخش خودکار هنوز پیاده نشده است.

توکن واقعی برای این تحویل ارائه نشده؛ تأیید اتصال زنده، مجوز تیم و معنای واحد متریک‌ها باقی مانده‌اند. هیچ عملیات تغییردهنده سرویس ابری در این مرحله اجرا نمی‌شود.

## مدل و گفتگوی فاز ۵

کلید فقط در سرور تنظیم می‌شود: `AI_API_KEY`، `AI_MODEL`، `AI_BASE_URL` (پیش‌فرض `https://api.openai.com/v1`)، `AI_API_STYLE` (`responses` یا `chat`) و `AI_TIMEOUT_MS` (پیش‌فرض ۲۰۰۰۰، بازه ۱۰۰ تا ۳۰۰۰۰). مدل پیش‌فرض انتخاب نشده؛ مدل باید function calling و سبک API انتخابی را پشتیبانی کند. کلیدها نباید پیشوند `VITE_` داشته باشند. پس از تغییر تنظیمات API را مجدداً اجرا کنید. در نبود کلید/مدل، گفتگو با پیام شفاف غیرفعال است.

`pnpm db:migrate` هر سه migration فعلی را اعمال می‌کند. `/workspace/assistant` گفتگوی حساب شخصی و `/demo/assistant` سناریوی مستقل دمو است. راهنمای کامل، مسیر تأیید، سقف اجرا و قراردادهای API در [AI_ASSISTANT.md](AI_ASSISTANT.md) است. فراخوانی واقعی مدل و ارائه‌دهنده لیارا در این تحویل بدون کلید/توکن تأیید نشده‌اند.

## فاز ۶ و پیکربندی فعلی

AI_MODELS فهرست شناسه‌های مجاز انتخاب مدل است؛ کلید Liara AI صرفاً AI_API_KEY است و به عنوان توکن PaaS استفاده نمی‌شود. درگاه فعلی با سبک chat آزموده شده است. در نصب تازه، secrets:init، db:generate و db:migrate را پیش از dev اجرا کنید؛ اکنون ۶ migration وجود دارد.

همان worker برنامه هم بررسی محلی و هم صف مستقل انتشار را اجرا می‌کند؛ خاموش بودن worker باعث ماندن انتشار تأییدشده در outbox/صف می‌شود. pnpm start:worker در build نیز هر دو را اجرا می‌کند. مسیر انتشار در `/workspace/deployments` است. توکن حساب PaaS فقط در فرم اتصال اختصاصی وارد می‌شود. راهنمای دامنه پشتیبانی و جریان تأیید در DEPLOYMENT_WORKFLOW.md است.
